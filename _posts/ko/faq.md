## 데이터 개인정보 보호 및 규정 준수

### 내 인프라에서 데이터가 유출되나요?

**아니요.** 은행 명세서 파서는 상태 비저장 라이브러리로 작동합니다. 구문 분석, PII 수정, 아카이브 추출 등 모든 처리는 로컬 런타임 메모리 내에서 발생합니다. API 호출, 클라우드 서비스, 원격 측정이 없습니다. XML 파서는 다음과 같이 강화됩니다.`no_network=True`, 파서 수준에서 모든 아웃바운드 액세스를 차단합니다. 귀하의 금융 데이터는 결코 귀하의 환경을 벗어나지 않습니다.

### PII 수정은 어떻게 작동하나요?

민감한 필드는 애플리케이션 로직에 도달하기 전에 마스크됩니다. 파서는 채무자 이름, 채권자 이름, IBAN 및 우편 주소를 식별하여 다음으로 대체합니다.`***REDACTED***`콘솔 출력 및 스트리밍 모드에서.

- CLI 출력 및 스트리밍 모드에서는 **수정이 기본적으로 켜져 있습니다**.
- **파일 내보내기**(CSV, JSON, Excel)는 다운스트림 처리를 위해 수정되지 않은 데이터를 유지합니다.
- **전체 데이터 수신 동의**`--show-pii`CLI에서 또는`redact_pii=False`API에서.

### 추출 프로세스가 결정적인가요?

**예 - 실행할 때마다 바이트 단위로 동일한 출력이 발생합니다.** 동일한 입력 파일이 주어지면 파서는 매번 동일한 결과를 생성합니다. 무작위성 없음, 모델 추론 없음, 경험적 샘플링 없음. CI는 가설을 통한 속성 기반 퍼징을 포함하여 100% 분기 적용 범위에서 467개 테스트를 통해 결정성을 강화합니다.

### 프로젝트는 어떤 규정 준수 표준을 따르나요?

이 프로젝트는 완전한 추적성을 갖춘 ISO 13485에 따른 문서를 유지합니다.

- 심각도/확률 점수 및 잔여 위험 평가가 포함된 정량화된 **위험 등록**.
- 5단계에 걸쳐 19개 단계로 구성된 **검증 및 검증 계획**.
- 영향 평가 및 롤백 프로토콜이 포함된 **변경 제어 절차**.
- 위험 수준 및 EOL 추적과 함께 모든 종속성을 다루는 **SOUP 레지스터**입니다.
- 구현 및 검증에 대한 설계 입력을 매핑하는 **추적성 매트릭스**입니다.

모든 릴리스에는 CycloneDX SBOM, SHA-256 체크섬 및 GitHub 빌드 출처 증명이 포함되어 있습니다.

## 성능 및 확장성

### 은행 명세서 파서는 얼마나 빠른가요?

성능 임계값은 모든 커밋마다 CI에서 검증됩니다.

| 미터법 | 값 |
|---|---|
| CAMT.053 처리량 | 초당 27,000개 이상의 트랜잭션 |
| PAIN.001 처리량 | 초당 52,000개 이상의 트랜잭션 |
| 트랜잭션당 대기 시간(CAMT) | 37마이크로초 |
| 트랜잭션당 대기 시간(PAIN.001) | 19마이크로초 |
| 첫 번째 결과까지의 시간 | < 2ms |

### 대용량 파일은 어떻게 처리되나요?

**제한된 메모리를 사용한 스트리밍 -- 파일당 50,000건의 트랜잭션으로 테스트되었습니다.** 사용`parse_streaming()`XML 파일을 증분적으로 처리합니다. 각 트랜잭션은 사전으로 생성됩니다. 메모리 증가를 방지하기 위해 처리 후에 요소가 지워집니다. 메모리는 파일 크기에 따라 확장되지 않습니다. 50K 트랜잭션 테스트(25MB 이상)는 10K 트랜잭션 테스트에 비해 2배 미만의 메모리를 사용합니다.

50MB를 초과하는 파일(예: 100,000개 이상의 결제가 포함된 호스트 간 PAIN.001 배치)의 경우 파서는 청크 기반 네임스페이스 제거를 사용하여 임시 파일을 통해 스트리밍합니다. 전체 문서는 메모리에 로드되지 않습니다.

### ZIP 아카이브는 어떻게 안전하게 처리되나요?

`iter_secure_xml_entries()`추출 전에 각 멤버의 유효성을 검사합니다.

- **항목 크기 한도**(항목당 기본 10MB)
- **압축되지 않은 총 크기 한도**(기본값 50MB)
- ZIP 폭탄을 방지하기 위한 **압축 비율 제한**(기본값 100:1)
- **암호화된 항목 거부**

디스크에 파일이 기록되지 않습니다. XML 바이트는 다음을 통해 파서에 직접 전달됩니다.`from_bytes()`.

### 여러 파일을 병렬로 구문 분석할 수 있나요?

**예.** 사용`parse_files_parallel()`작업을 여러 곳에 분산시키는 것`ProcessPoolExecutor`:

```python
from bankstatementparser import parse_files_parallel

results = parse_files_parallel([
    "statements/jan.xml",
    "statements/feb.xml",
    "statements/mar.xml",
])
for r in results:
    print(r.path, r.status, len(r.transactions), "rows")
```

## 지원되는 형식

### 어떤 은행 명세서 형식이 지원되나요?

| 체재 | 기준 | 파일 유형 | 파서 클래스 |
|---|---|---|---|
| CAMT.053 | ISO 20022 은행-고객 명세서 | `.xml` | `CamtParser` |
| 고통.001 | ISO 20022 학점 이전 개시 | `.xml` | `Pain001Parser` |
| CSV | 일반 은행 수출 | `.csv` | `CsvStatementParser` |
| OFX | 개방형 금융거래소 | `.ofx` | `OfxParser` |
| QFX | 금융교류를 촉진하다 | `.qfx` | `QfxParser` |
| MT940 | SWIFT 표준 | `.mt940`, `.sta` | `Mt940Parser` |

### 파서는 ​​CAMT.053의 은행별 방언을 처리합니까?

**예 - 네임스페이스에 구애받지 않도록 설계되었습니다.** 파서는 처리하기 전에 XML 네임스페이스를 제거하여 모든 CAMT.053 변형(`camt.053.001.02`, `camt.053.001.04`또는 독점 은행 래퍼) 네임스페이스별 구성이 없습니다. XPath는 네임스페이스 URI가 아닌 대상 요소 구조를 쿼리합니다.

CAMT를 맞춤형 봉투에 포장하는 은행의 경우 다음을 사용하세요.`from_string()`또는`from_bytes()`내부 문서를 직접 공급합니다.

### 맞춤 CSV 열 헤더를 표준 스키마에 매핑할 수 있나요?

**예 - 자동 정규화, 구성 없음.**`CsvStatementParser`일반적인 헤더 변형을 인식합니다.`"Date"`, `"Transaction Date"`, `"Booking Date"`모두에 매핑됩니다.`date`필드.`"Amount"`, `"Value"`, `"Sum"`매핑하다`amount`. 신용/차변 항목 분할(예:`"Credit"`그리고`"Debit"`)이 자동으로 감지되어 하나의 서명된 금액으로 결합됩니다.

### 출력 형식은 무엇입니까?

모든 파서는 일관된 열 유형을 사용하여 표준화된 Pandas DataFrame을 생성합니다.

| 체재 | 주요 열 |
|---|---|
| **CAMT** | `Amount`, `Currency`, `DrCr`, `Debtor`, `Creditor`, `Reference`, `ValDt`, `BookgDt`, `AccountId` |
| **고통.001** | `PmtInfId`, `PmtMtd`, `InstdAmt`, `Currency`, `CdtrNm`, `EndToEndId`, `MsgId`, `CreDtTm`, `NbOfTxs` |
| **CSV/OFX/QFX/MT940** | `date`, `description`, `amount`(정규화) |

CSV, JSON, Excel로 내보내거나 Polars DataFrames로 변환할 수도 있습니다.

## 재무 워크플로

### 파서는 ​​다중 통화 명령문을 어떻게 처리하나요?

**각 거래는 원래 통화를 유지하며 암시적 변환은 없습니다.**`Currency`필드는 XML에서 추출됩니다.`Ccy`트랜잭션당 속성. 다중 통화 명세서는 그대로 유지됩니다. 그만큼`get_account_balances()`메소드는 원래 통화 코드를 사용하여 계정당 기초 및 마감 잔액을 반환합니다. 교차 통화 조정은 환율 소스를 제어하는 ​​다운스트림 논리에 맡겨집니다.

### 파서는 ​​나가는 형식과 들어오는 형식을 모두 지원합니까?

**예.**`Pain001Parser`ISO 20022 PAIN.001 신용 이전 시작 파일(지불)을 처리합니다.`CamtParser`CAMT.053 은행-고객 명세서 파일(수신 보고)을 처리합니다. 둘 다 스트리밍, PII 수정 및 CSV, JSON 및 Excel로 내보내기를 지원합니다. 사용`detect_statement_format()`형식을 자동으로 식별합니다.

### 거래 항목의 형식이 잘못되면 어떻게 되나요?

동작은 구문 분석 모드에 따라 다릅니다.

- **`parse()`(일괄 모드)** -- 필수 필드가 누락된 잘못된 형식의 항목(`Amount`, `Currency`, 또는`CdtDbtInd`)은 경고 로그와 함께 건너뜁니다. 명령문의 나머지 부분은 정상적으로 구문 분석됩니다.
- **`parse_streaming()`(스트리밍 모드)** -- 구문 분석 오류는 즉시 예외로 전파됩니다. 자동 데이터 손실이 없습니다. 이러한 빠른 실패 동작은 모든 거래를 설명해야 하는 금융 워크플로우를 위해 의도된 것입니다.

### 중복 제거는 어떻게 작동하나요?

그만큼`Deduplicator`클래스는 설명 가능한 신뢰도 점수를 사용하여 정확한 중복과 의심되는 일치 항목을 감지합니다.

```python
from bankstatementparser import CamtParser, Deduplicator

parser = CamtParser("statement.xml")
dedup = Deduplicator()
result = dedup.deduplicate(dedup.from_dataframe(parser.parse()))

print(f"Unique: {len(result.unique_transactions)}")
print(f"Exact duplicates: {len(result.exact_duplicates)}")
print(f"Suspected matches: {len(result.suspected_matches)}")
```

### 종속성은 무엇입니까?

라이브러리에는 5가지 직접적인 종속성이 있습니다.

- `lxml`-- 보안 강화를 통한 XML 구문 분석
-`pandas`-- DataFrame 및 데이터 조작
-`openpyxl`-- 엑셀 내보내기

모든 종속 항목에는 SHA-256 해시 잠금 버전이 있습니다. CycloneDX SBOM은 모든 런타임 구성 요소를 매핑합니다.

### 은행 계좌 명세서 파서는 pyiso20022와 어떻게 비교되나요?

pyiso20022는 ISO XML 스키마에서 Python 데이터 클래스를 생성하는 광범위한 ISO 20022 툴킷입니다. 스키마 유효성 검사를 통해 광범위한 ISO 20022 메시지 유형(PACS, PAIN, CAMT, ADMI)을 다룹니다. 은행 계좌 명세서 파서는 스트리밍 지원, PII 수정, 중복 제거 및 비ISO 형식(CSV, OFX, QFX, MT940)을 포함한 6가지 형식의 통합 API를 갖춘 은행 계좌 명세서 구문 분석을 위해 특별히 제작되었습니다. 프로덕션 등급 보안을 통해 은행 명세서를 DataFrame으로 구문 분석해야 하는 경우 Bank 명세서 구문 분석기를 사용하세요. 전체 ISO 20022 메시지 카탈로그로 작업해야 하는 경우 pyiso20022를 사용하세요.

### SWIFT ISO 20022 마이그레이션 마감일은 언제인가요?

SWIFT는 단계별 마이그레이션 타임라인을 발표했습니다.

- **2026년 11월**: 구조화된 주소와 하이브리드 주소가 필수가 됩니다. MT101 다중 명령 메시지는 거부됩니다. 사례 관리 1단계가 시작됩니다.
- **2027년 11월**: 모든 금융 기관은 CAMT.053 명세서를 기본적으로 수신할 수 있어야 합니다. SWIFT는 MT를 ISO 형식으로 변환하는 것을 중단합니다.
- **2028년 11월**: MT940, MT942, MT950, MT900, MT910이 완전히 중단됩니다. 이는 CAMT.052, CAMT.053 및 CAMT.054와 동등한 항목으로 대체됩니다.

Bank 명세서 파서는 레거시 MT940 형식과 최신 CAMT.053/PAIN.001 형식을 모두 지원하므로 전환 기간에 이상적입니다.
